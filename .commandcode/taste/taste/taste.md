# Taste
- Runs a BMad-style governed workflow: feature work is driven through named agent personas (e.g. Product Manager, Business Analyst, Architect), each activated via its skill (`activate_skill`) with customization resolved from `.agents/skills/<skill>/customize.toml` plus `_bmad/` config and team/personal override files, and durable artifacts written under `_bmad-output/planning-artifacts/`. Expects these conventions to be followed rather than improvised. Confidence: 0.75
- Prefers staged, gated progression for larger feature work: scoped research/requirements analysis first → architecture ratification (with an adversarial review gate before an artifact is marked final) → engineering scaffold; confirms scope with the user via clarifying questions before acting, and does not write feature code until the architecture is ratified. Confidence: 0.7
- Expects technical decisions and claims (CLI contracts, on-disk layouts, flags/exit codes, existing code behavior) to be verified against the live environment and repo code — not asserted from training data — and evidence recorded alongside the decision (evidence log / memlog). Confidence: 0.7
- Prefers having the project running locally so they can browse/interact with the UI to verify feature work themselves (asked twice to get the app up and running, then to "hand over" with URLs/next steps), rather than relying only on deferred CI/test gates. Confidence: 0.7
- When contributing to an upstream/external repo, mirrors that project's own conventions: reads its CONTRIBUTING.md/commitlint/license and, before drafting, studies recently merged/approved PRs (e.g. the OpenCode provider-add and maintainer PRs) to copy their title and body structure (`## Summary` / `## What changed` with grouped bullets) rather than inventing a format. Confidence: 0.75
- When local work bundles an upstream-appropriate code fix with fork-specific infra (CasaOS manifests, Dockerfile, Jenkins), delegates to the agent the judgment that the fix deserves its own PR and expects it "properly like before": branch cut from upstream `main` (not the fork's `production`), only the code slice carried over (fork-specific files excluded), any hunks belonging to other still-open PRs stripped so the diff is minimal and self-contained rather than duplicating/depending on them, server + client typechecks run before opening, then the local working branch (and stashed local changes) restored afterwards. Re-stated in a follow-up session with the same delegation ("continue and after your check commit and push to production ... if you think then create another PR for that again if it is necessary"), i.e. the agent should decide autonomously whether another PR is warranted rather than ask. Confidence: 0.8
- Treats agent orchestration/tooling directories (`.agents/`, `_bmad/`, `_bmad-output/`, `.commandcode/`) as repo assets that belong in version control: explicitly asks for them to be committed to the production branch alongside the code, not left untracked/ignored. Confidence: 0.65
- Once given a high-level go-ahead ("yes", "take all necessary steps", "take initiative"), prefers the agent to drive the whole multi-stage flow autonomously — resolving blockers (e.g. killing dev-server processes that lock build outputs), running local quality gates (typecheck/lint/build) so the branch is green, and opening the PR — rather than pausing at each step; still wants a clear handover of what was done vs. what remains theirs to do. Confidence: 0.75
- Directs via very terse, informal, lowercase messages ("i stopped running now continue", "suggested version gives erroe", "again jankins build aspp image fdailed", "in casaos there need an adjustment in vps server...") and expects the agent to infer the current state and resume the task autonomously — after the user manually aborts a slow CI build, "continue" means check the job state, re-trigger the run, and keep driving it forward; a terse error report (even on a recurring issue, with no new context) means investigate the latest build log, root-cause, fix, commit/push, and monitor the resulting build — all without asking clarifying questions — e.g. "great with shared now claude auto get its connection from vps main but cursor and commandocde missed why ?" means investigate the deployed container, root-cause the partial failure, and report back; a bare mismatch report like "in command code cli it says Authenticated ... but in ui it says not connected" means trace how the server derives provider status from the CLI's own output and root-cause the discrepancy. Confidence: 0.96
- Though terse bug reports generally mean "investigate autonomously", when the failure is genuinely ambiguous about which layer failed (container won't start vs. UI shows an error vs. CLI errors inside the container vs. a proxy in between), he promptly answers targeted multiple-choice clarifying questions picking the affected layer — so a quick structured question (concrete options, not open-ended) is acceptable in that genuinely ambiguous case before the agent root-causes the chosen path; observed answering three consecutive MCQs in one diagnostic session (access method → built-in vs external proxy → proxy type) to converge on the cause. Confidence: 0.65
- Prefers to keep credentials/secrets out of the agent's hands: when stored Docker Hub creds were stale, he chose the "I'll log in myself in WSL" option over sharing a PAT — when auth is missing, the agent should ask the user to authenticate themselves rather than request or paste secret tokens. Confidence: 0.55
- When verification work is being done, he expects the agent to run the checks itself in one fresh complete pass and FIX what fails before handing over — he pushes back ("look i told you...") if the agent instead hands him diagnostic command lists to run on a remote, or reports piecemeal partial status; "check automatically ... if not then fix then handover to me" means deliver a working, validated state, not open homework for the user. Reinforced at the end of a long CasaOS session: after many partial local tests he demanded one fresh complete local WSL pass through every provider's auth status with failures fixed before any handover ("look i told you ro run wsl local fresh ly then check automaitaclly all the all the agent get by cloudcli ui or not if not then fix then handover to me"). Confidence: 0.75
